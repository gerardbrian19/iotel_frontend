# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

IOTEL — the storefront and operations app for Goldcomm Corporation (two-way radio equipment). Angular 21 + ng-zorro-antd 21 + Tailwind CSS 4, standalone components and signals, strict TypeScript. Currently a **prototype**: auth, user profiles, products, favorites, addresses, service bookings, chat, orders and checkout are all on Firebase; payments go through PayMongo, live with **QR Ph only** until Goldcomm's account is verified, or by bank / GCash transfer that staff verify (see "Payments").

## Commands

```bash
npm start                                # ng serve → http://localhost:4200
npm run build                            # production build (budgets: 1MB initial warn/2MB error, 4kB/8kB per component style)
npm run watch                            # dev-config build in watch mode
npx prettier --write <files>             # printWidth 100, single quotes; no lint script exists
npm run functions:build                  # tsc for the Cloud Functions in functions/ (own package.json; npm install there)
firebase deploy --only functions         # deploys functions/ (asia-southeast1); needs the SMTP_USER/SMTP_PASS and PAYMONGO_* secrets
firebase deploy --only firestore:rules,storage   # Firestore + Storage rules (storage.rules: transfer screenshots, receiver QR codes)
PAYMONGO_SECRET_KEY=sk_test_… npm run paymongo:webhook -- <url> | --list   # register the PayMongo webhook, print its secret
npm run auth:enable-totp -- [--check]    # turn on authenticator-app MFA for the project (Admin SDK, repo-root key)
npm run auth:reset-mfa -- <email>        # last-resort: remove an account's authenticator app
```

- **There is no test setup.** Unit and e2e tests (Vitest, Playwright, all `*.spec.ts`, `e2e/`) were deliberately removed at the maintainer's request; don't add or restore them unless asked.
- Component generation defaults to SCSS (`ng g component` → `.scss`).

## Architecture

**Three role portals, each a lazy-loaded route tree** ([app.routes.ts](src/app/app.routes.ts)): `/auth`, `/customer`, `/admin`, `/staff`. Each protected tree is gated by `authGuard` + `roleGuard('<role>')` (functional `CanActivateFn`s in `core/guards/`) and renders inside its own shell component (`features/<role>/shell/`) with children loaded via `loadComponent`. No session → `/auth/login`. Admin and staff have parallel feature folders (dashboard/orders/inventory/messages) that share services but not components; the two-panel chat UI lives in `shared/components/chat-panel` and is reused by all roles.

**Data layer (`core/services/`)**
- Services hold state as a private `signal<T[]>` (filled by Firestore `onSnapshot` listeners; there are no mock constants left), expose it via `.asReadonly()`, and return `Observable`s from their methods. Components call `.subscribe()` on those methods (one-shot, no teardown needed today). Preserve this shape — signals for reads, Observables for writes — when changing services, so components don't need to change.
- **Auth is real (Firebase Auth + Firestore `users/{uid}` profile).** `AuthService` exposes `currentUser`/`isLoggedIn`/`hasRole` signals and async `login`/`register`/`logout`. The role lives in the profile doc (`customer` | `staff` | `admin`), not in Auth. `AuthService.ready` is awaited by `provideAppInitializer` in `app.config.ts`, so the session is restored before routing and the guards (`authGuard`, `roleGuard(role)`, `guestGuard` on `/auth`) stay synchronous; a signed-in user on the wrong portal is redirected to their own. Public sign-up (`/auth/register`) always creates a `customer`; admins create staff/admin accounts and change roles at `/admin/users` (`UserService`, which creates accounts on a throwaway secondary Firebase app so the admin isn't signed out). Role rules (users, `products`, `favorites`, `addresses`, `services`, `bookings`, `bookingSlots`, `conversations`, `orders`, `counters`) are enforced in `firestore.rules`, which is **not deployed by default** — deploy with `firebase deploy --only firestore:rules`; without it every profile read fails. The first admin must be promoted by hand in the Firebase Console (edit that user's `users/{uid}` doc, `role: 'admin'`). Form validators shared by auth forms are in `shared/utils/validators.ts`; Firebase error → message mapping is in `core/firebase/auth-errors.ts`.
- **Two-step sign-in** (plan and setup steps: `docs/auth-upgrade-plan.md`). **Feature-flagged, turned on 2026-10-11:** `TWO_STEP_SIGN_IN` in `core/auth/auth-flags.ts`, mirrored by `twoStepSignIn()` in `firestore.rules` and `functions/src/flags.ts` (change all three, redeploy rules + functions). Off = email + password signs everyone in (accounts that already enrolled TOTP are still asked for it by Firebase Auth); on = everything below. A password never signs anyone in by itself: `AuthService.login()`/`register()` leave `currentUser` null and set `pendingStep` (`email-code` | `totp-code` | `totp-enroll`), which the login page renders with `features/auth/second-step`; the user is published only once the step is done. **Customers** get a 6-digit code by email at every sign-in: the `sendLoginCode` / `verifyLoginCode` callables in `functions/src/auth.ts` (hashed code in `loginCodes/{uid}`, 10-min expiry, 60 s resend cooldown within one sign-in, 5 sends/hour, 5 wrong tries) send it from `no-reply@iotel.app` through Resend SMTP (nodemailer; `SMTP_USER` = `resend` / `SMTP_PASS` = Resend API key secrets, host/port/`MAIL_FROM` in `functions/.env`; Brevo was dropped after a bounce suspension) and, on success, set the custom claim `otpAuthTime = auth_time` and `emailVerified`. **Staff/admins** use Firebase TOTP (Identity Platform): first sign-in → emailed code if the email isn't verified → set up the app (QR via `nz-qrcode`) → signed out → password + app code. `firestore.rules` mirrors this: `signedIn()` = token has `otpAuthTime == auth_time` or `firebase.sign_in_second_factor == 'totp'`, `isStaff`/`isAdmin`/`isStaffOrAdmin` also require TOTP, and only reading/creating your own profile uses the bare `authed()`. A restored session without the step counts as signed out (`AuthService.restore`; it is deliberately not signed out, because the Firebase session is shared by all tabs and another tab may be on its code step). Admins can reset someone's authenticator (`resetAuthenticator` callable) or send a password-reset email from `/admin/users`. Password reset: `/auth/forgot-password` (only registered accounts: the `checkResetEmail` callable looks the email up, Auth user + `users/{uid}` profile, rate-limited to 10 checks/hour per IP in `resetChecks/`; unknown emails get "isn't registered") and `/auth/reset-password` (currently unused: Firebase only accepts an action URL on a Firebase Hosting domain, and the site is on Vercel, so reset links open Firebase's default handler, whose Continue button returns to `/auth/login`; using this page would mean sending reset emails ourselves through Resend with an Admin-SDK-generated link). `shared/components/account-security` (customer Settings → Account Security, `/staff/account`, `/admin/account`) changes the password (re-auth, TOTP code if needed, then sign-out) and replaces the authenticator. `FUNCTIONS` token in `core/firebase/firebase.ts` (region `asia-southeast1`).
- **Profile picture** lives on the profile doc as `photoURL`, a 256×256 JPEG data URL (not Firebase Storage, which is only used for transfer screenshots and receiver QR codes): `shared/utils/avatar-image.ts` crops/resizes the chosen file, `AuthService.setPhoto()` writes it, and `firestore.rules` lets users change only `name`, `photoURL` (≤150 kB, `data:image/jpeg;base64,`), `gender`, `dateOfBirth`, `phone` and `bio` (≤300 chars), saved by the profile form through `AuthService.updateDetails()`. Only the owner and admins can read `users/{uid}`, so other people's photos (e.g. in chat) can't be shown without denormalising. Mobile numbers everywhere (profile, addresses, bookings, checkout) are `09XXXXXXXXX`: `phMobile`/`normalizeMobile` in `shared/utils/validators.ts`, the `appMobileInput` directive on inputs, `validMobile` in the rules and `localMobile` in `functions/src/payments.ts`. Admins remove customer accounts with the `deleteCustomerAccount` function, which leaves a `deletedAccounts/{uid}` marker so a leftover ID token can't re-create the profile.
- **Terms of Service + Privacy Policy** are data in `core/legal/legal-documents.ts` (written from the app's real behaviour; `confirm` blocks mark details Goldcomm still has to supply, and `draft: true` shows a banner), rendered by `shared/components/legal-document` in the register page's modal and on the public `/legal/terms` and `/legal/privacy` pages. Registration requires the consent checkbox, and `AuthService.register()` writes `legalAcceptance { termsVersion, privacyVersion, acceptedAt }` on the new profile (validated in `firestore.rules`, immutable afterwards). Bump `TERMS_VERSION`/`PRIVACY_VERSION` whenever the text changes; there is no re-acceptance prompt for existing users yet. Profiles created any other way (admin-created accounts at `/admin/users`, the login fallback for an account with no profile, anyone registered before this) have **no** `legalAcceptance`; a future re-acceptance prompt should cover them too.
- **Customer Settings is trimmed on purpose.** The menu and routes for Bank Accounts / Cards (`payment-methods`), My Wallet, the Preferences group (notifications, privacy, language, chat) and Linked Accounts are **commented out** in `settings.component.ts` / `settings.routes.ts`, and the assistant's links to them too; the component folders are kept but unrouted. Account Security is routed (it's the shared `account-security` component). We never store card/bank/wallet data; customers enter it on PayMongo's page.
- **Products are real (Firestore `products/{slug}`).** `ProductService` streams the whole collection into a signal via `onSnapshot` while someone is signed in (an `effect` on the uid; cleared on sign-out) and exposes `products` (all), `activeProducts` (storefront), `byId`, `loading`, `error`. `toProduct()` maps a doc to the UI shape: `srp` → `price` (`null` = price on request, not purchasable), and `inStock` is derived (`isActive && stock > 0`), never stored. `dealerPrice` and the other source-sheet fields are not mapped. Writes (`add/update/remove/setActive/adjustStock`) return Observables that reject on permission errors. Seed with `npm run seed:products` (`scripts/seed-products.mjs`, Admin SDK). `catalog` filters by category tab (counts reflect other filters), search (name/brand/model/keywords), min/max price, in-stock only, sort, and paginates 24 per page; `shared/components/product-card` and `product-detail` are shared with the favorites page.
- **Orders + checkout are real** (`OrderService`, `orders/{id}`, `counters/orders`; UI: `customer/{checkout,order-confirmation,orders}`, `staff/orders`, `admin/orders`, shared `order-actions` + `order-detail`). Customers see their own orders, staff/admins all of them, live via `onSnapshot`. Checkout blocks on `CartService.problems` (item gone, out of stock, not enough stock, price changed — `cartProblems()`; `fitToStock()` fixes the cart, and an effect in `CartService` keeps line prices/names in step with the live catalog), then `OrderService.checkout()` calls the `createOrderCheckout` function, which re-checks and prices the cart from `products`, writes the order + `counters/orders.last + 1` in one transaction and returns a PayMongo checkout URL; the app clears the cart and redirects there. **Clients can't create orders or write `counters`** (rules). Flow: `Pending` (payment `Unpaid`) → PayMongo webhook sets `Paid` → `startProcessing` → `Processing` → `ship` (courier + optional tracking number) → `Shipped` → `markOutForDelivery` → `Out for Delivery` (`outForDeliveryAt`; the customer sees "out for delivery to <their address>", `deliveryAddress()` in `order-view.ts`) → `markDelivered` → `Delivered` (the rules still allow Shipped → Delivered for older app builds; the app requires the new step). Customers and staff can cancel only a Pending **unpaid** order with no transfer proof under review; a paid order is cancelled only via `OrderService.refund()` (`refundPayment` function: PayMongo refund + cancel + restock if Processing). **Cancellation requests** (`functions/src/cancellations.ts`): on a paid Pending/Processing order the customer's Cancel order button asks instead (`requestOrderCancellation`: reason from `CANCEL_REQUEST_REASONS`, mirrored in the function, + 10–500 char explanation, plus `refundTo` (their GCash `09XXXXXXXXX` or bank name/account, `refundAccountOf` in `payment-common.ts`) when the refund is manual → `cancelRequest { status: 'pending', … }` on the order, functions-only); staff/admins approve by refunding (`refundPayment` marks the request `approved` and sets `cancelledBy: 'customer'`) or `rejectOrderCancellation` with a note the customer sees. While a request is open, `staffAction()` is `review-cancel` and start-processing / ship are refused (app-side only). Queue: `/staff/cancellations` and `/admin/cancellations` (shared `cancellation-queue`, menu badges, admin dashboard alert). Unpaid **PayMongo** orders are cancelled by `expireUnpaidOrders` after 60 min (`cancelledBy: 'system'`); transfer orders never are. **Stock is deducted when staff start processing** (one transaction over the order + its products; fails with the shortfall if stock ran out), not at checkout, so abandoned checkouts never hold stock. Admins use the same actions as staff (there is no free-form status dropdown; it would break the stock accounting). `core/orders/order-view.ts` holds the pure status/payment badges, next-step hints, `canPay`/`canRefund`, `staffAction()` and the tracker `orderTimeline()`. `/customer/orders/:id/confirmation?payment=success|cancelled` is PayMongo's return URL. Staff notifications to the customer are just the status on their order (no chat message per order yet).
- **Payments: PayMongo, bank / GCash transfer, or on site** (PayMongo: hosted Checkout Sessions; setup, test cards and going live: `docs/paymongo-setup.md`). Backend in `functions/src/payments.ts`: `createOrderCheckout`, `createBookingCheckout`, `paymongoWebhook` (HMAC-checked `Paymongo-Signature`, idempotent via `paymongoEvents/{eventId}`; with the manual-payment functions, the only writers of `payment.status = 'Paid'`), `refundPayment` (staff/admin), `expireUnpaidOrders` (every 15 min) and `onOrderCancelled`/`onBookingCancelled` (expire the checkout of a cancelled unpaid order/booking). **Invoices** (`functions/src/invoices.ts`, `docs/paymongo-setup.md` → Invoices): an HTML email + PDF (pdfkit; `INV-000123` from `counters/invoices`, kept on resends) sent to the customer's Auth email, automatically when PayMongo marks a payment Paid (`onOrderPaid`/`onBookingPaid`), and for transfers / on-site payments only when staff tick "Email the invoice" when approving / recording (`sendInvoice` on those callables) or press Send invoice (`sendInvoiceEmail`; shared `shared/components/invoice-status`). Stored as `invoice` (`InvoiceInfo`) on the order/booking, backend-only. The mailer (Resend SMTP) is shared in `functions/src/mail.ts`. Secrets `PAYMONGO_SECRET_KEY` (`sk_live_…` since 2026-10-27; the account is activated but not verified, so the checkout offers **QR Ph only** until then) and `PAYMONGO_WEBHOOK_SECRET` (the live webhook's); `APP_ORIGINS` in `functions/.env` whitelists return URLs. Orders and bookings share the `Payment` shape (`provider: 'paymongo'`, `status` Unpaid/Paid/Refunded, `amount`, `method` as reported by PayMongo, `checkoutSessionId`/`checkoutUrl`, `paymentId`, `refundId`, timestamps); clients never write it. App side: `core/payments/payment-methods.ts` (`toPayment`, `paymentMethodLabel`, `ACCEPTED_PAYMENT_METHODS`, `UNPAID_ORDER_MINUTES`). The accepted methods (`PAYMENT_METHOD_TYPES` in the function, `ACCEPTED_PAYMENT_METHODS` in the app), the 60-min TTL and `SHIPPING_FEE` are mirrored between `functions/` and the app. No Cash on Delivery.
- **Manual payments** (`docs/manual-payments.md`; `functions/src/manual-payments.ts`, shared helpers in `functions/src/payment-common.ts`). `Payment.provider` is `paymongo` | `manual` | `onsite` (missing = `paymongo`). **Transfers** (orders and bookings): `createOrderCheckout` with `provider: 'manual'` creates the order without a PayMongo session (`payment.manual.state: 'awaiting'`); the customer uploads a screenshot to Storage (`paymentProofs/{uid}/{order|booking}-{id}/…`, ≤ 5 MB, shrunk by `shared/utils/proof-image.ts`) and calls `submitManualPayment` (reference number, amount, sent time; one use per receiver + reference via `manualReferences/`; ≤ 5 attempts); staff `reviewManualPayment` approve (→ Paid, `method` `gcash` / `bank:<Bank>`, `paymentId` = reference) or reject with a reason (customer resends; old attempts in `manual.history`). While a proof is `submitted`, nobody can cancel the order/booking or change the booking's quote (`proofUnderReview()` in rules and `core/payments/manual-payments.ts`). **On site** (bookings only): staff tick `quote.allowOnsite` when quoting; the customer's `chooseOnsitePayment` makes it "Booked · Pay on site" (still `Confirmed`); staff `recordOnsitePayment` (method, amount, receipt, optional complete). Refunds of transfers/on-site payments **and PayMongo QR Ph payments** (`refundsManually()`, mirrored in `functions/src/payment-common.ts` and `core/payments/payment-methods.ts`: PayMongo answers "Refunds are not allowed for payments with source type qrph" on this account) go through `refundPayment` with a required `refundReference` (staff send the money back themselves, to the request's `refundTo` if there is one) and an optional screenshot (`shared/components/refund-proof-picker` → `core/payments/refund-proof.ts` uploads to Storage `refundProofs/{customerId}/{order|booking}-{id}/…`, staff/admin write, the customer and staff read; kept as `payment.refundProofPath`, shown in `order-detail` and the booking panel). **Receivers** (`paymentReceivers/{id}`, `PaymentReceiverService`, admin CRUD at `/admin/payment-receivers`; QR in Storage `paymentReceivers/{id}/…`; `validReceiver` in rules; customers read only active ones; payments keep a `receiver` snapshot, so deleting is safe). App side: `ManualPaymentService` (`toVerify` feeds the `/staff/payments` + `/admin/payments` queue, `shared/components/payment-review-queue`, and the menu badges), `shared/components/manual-payment-panel` (customer), `payment-proof` (staff approve/reject), `storage-image` (Storage images via `getDownloadURL`). `FIREBASE_STORAGE` token in `core/firebase/firebase.ts` (emulator port 9199).
- **Admin dashboard + activity log** (`features/admin/dashboard`, `features/admin/activity`). The dashboard has KPIs, a sales chart switchable Daily (30 days) / Weekly (12 Mon–Sun weeks) / Monthly (12 months) (`salesSeries()` in `core/orders/sales-view.ts`, delivered orders only), a Payments card (`core/payments/payment-summary.ts`: collected / this month / awaiting / refunded / still-to-refund, orders vs bookings, by method), a **Sales & Revenue Report** card (`dashboard/sales-report`, rules in `core/payments/sales-report.ts`: a day, Mon–Sun week or month; All / GCash only / Bank transfer only; counts orders + bookings with payment `Paid` and not Cancelled, dated by `payment.paidAt` (else `createdAt`), channel from `revenueChannel()`; combined = GCash + bank, other methods listed separately; card totals and the downloads come from the same `SalesReport`: Excel `.xlsx` (Summary + Transactions sheets via the dependency-free `shared/utils/xlsx-writer.ts`, built in `sales-report-files.ts`), CSV (`IOTEL_<Period>_Sales_Report_….csv`, BOM + RFC 4180) and a printable page for Save as PDF (`reportPrintHtml`), from the already-streamed orders/bookings, admin route only), a Service Bookings card (`core/booking/booking-summary.ts`), recent activity, low stock, order status and category stock. **The activity log** (`activityLog/{id}`, `ActivityService`, `/admin/activity`: filters + CSV export) is written server-side by `onDocument…WithAuthContext` triggers in `functions/src/activity.ts` on `orders`, `bookings`, `products`, `services`, `paymentReceivers` and `users`, which get the acting user from Firestore's `authId`; writes made by functions are attributed from the document (the order's customer, `payment.refundedBy` set by `refundPayment`, PayMongo, or System). `resetAuthenticator`/`deleteCustomerAccount` log their own entries (`logActivity`). Clients write only their own `account.signIn` entry (`AuthService.recordSignIn`, checked in `firestore.rules`); admins read; nobody edits. Needs `firebase deploy --only functions,firestore:rules`.
- **Landing page** (`features/landing`, guests only): `hero-slideshow` (3 remote images, 5 s auto-advance, pauses on hover/focus) and `best-sellers`. Guests can't read `products`, so Best Sellers reads `showcase/bestSellers` ({ productIds, products, updatedAt }), a public copy with no `dealerPrice` (`ShowcaseService`, started in `app.config.ts`). `npm run sync:showcase` (Admin SDK; top sellers by quantity ordered, or `--ids`) picks the products; staff/admin sessions only refresh their price/stock, never the ranking. "View Product" / "Explore Products" point at `/customer/catalog`, and `authGuard` → login `?returnUrl=` brings the visitor back after sign-in or sign-up (the login ↔ register links keep the param; `shared/utils/return-url.ts` only accepts paths inside the user's own portal). **Deploy `firestore.rules` together with this frontend**: the old `users` create rule rejects `legalAcceptance`, so sign-up fails against it.
- **Product reviews** (`functions/src/reviews.ts`, `ReviewService`, `productReviews/{productId}_{uid}`): on a Delivered order the customer's "Rate products" (`shared/components/order-reviews`) sends 1–5 stars + optional comment (≤ 500) per product through `submitProductReview`, which checks the order is theirs, delivered and contains the product, stores the review with a shortened name ("Juan D.") and moves the product's `ratingSum`/`ratingCount` in the same transaction (one review per customer and product; resending replaces it). `Product.ratingAverage`/`ratingCount` are derived in `toProduct()` and excluded from `ProductInput`. Shown with `shared/components/star-rating` on product cards and in `product-detail` (summary, star breakdown, review list). Rules: signed-in users read, nobody writes. **Moderation**: `/admin/reviews` and `/staff/reviews` (shared `reviews-manager`: stats, filters by product / stars / visible-hidden / search, the reviewer's full name and order code from `OrderService`; `?product=<id>` pre-filters, linked from the admin Products page's Rating column). Admins hide/show with `setReviewHidden`, which moves the doc between `productReviews` and `hiddenReviews/{same id}` (staff/admins and the author read it) and adjusts the product's totals; a customer editing a hidden review keeps it hidden.
- **Favorites** live in `users/{uid}/favorites/{productId}` (`FavoritesService`, customers only; page at `/customer/favorites`, heart badge in the shell header). `ProductActions` holds the add-to-cart / like / share behaviour used by the card and detail dialog.
- **Service bookings + chat are real** (`BookingService`, `MessageService`, `services/`, `bookings/`, `bookingSlots/`, `conversations/{id}/messages/`). Flow: customer books a service at `/customer/services` (date + slot from live availability, plus a description of the problem) → status `Pending`, and a chat thread is opened in the same batch → staff/admin and customer discuss the problem, quotation and any date change in chat (`/customer|staff|admin/messages`, `?conversation=<id>` deep-links a thread) → staff press "Send quote" in the booking panel (`Confirmed`, shown as "Awaiting payment"; `quote.amount` ≥ ₱20, PayMongo's minimum) → the customer presses Pay (`BookingService.payQuote()` → `createBookingCheckout`, which reuses the open checkout unless the quote changed) → PayMongo's webhook sets the booking and its payment `Paid` and posts the event in the chat (or the customer pays by transfer / on site, see "Manual payments") → staff mark it `Completed`. The slot is held from the request on, but the booking is only called confirmed/booked once it is paid (status labels: Requested → Awaiting payment → Booked · Paid). Staff can re-quote until it's paid; a paid booking is cancelled only via `refund()` (frees the slot). PayMongo returns to `/customer/services?booking=<id>&payment=…`. Every status change also posts an `event` message in the thread. Availability: one booking per slot; each taken slot is a `bookingSlots/{date}T{HH:mm}` doc created/deleted in the same batch as its booking, so the doc id is the lock (creating an existing id is an update, which the rules deny). Business hours, lead time and slot list live in `core/booking/schedule.ts` and are mirrored in `firestore.rules` (slot times). Services are seeded with `npm run seed:services` and managed by staff and admins at `/admin/services` and `/staff/services` (shared `shared/components/services-manager`; writes in `BookingService` `addService`/`updateService`/`setServiceActive`; rules `validService`, staff or admin). A service has `pricing` (`fixed` | `starting` | `quote`, missing = `starting`; `quote` must store `price: 0`; price ≤ `SERVICE_MAX_PRICE` ₱10,000,000, also in the rules), optional `category`, `duration`, `imageUrl`, and `isActive` (missing = active); labels come from `core/booking/service-view.ts`. Customers and the assistant see only `activeServices`, and `validNewBooking` in the rules only accepts an existing, active service. Services are never deleted (the rules deny it, since they can't check for bookings); they are retired by deactivating them. Bookings keep their own `serviceName`/`servicePrice`. `shared/components/booking-panel` (role-aware actions, used in the customer list, staff/admin board `shared/components/bookings-board` and above the chat), `slot-picker` and `chat-panel` are shared across all roles. Conversations keep `customerUnread`/`staffUnread` counters; `Conversation.unreadCount` is the viewer's own. Customers can spam bookings (rules can't rate-limit) and slot capacity is fixed at one.
- **IOTEL Assistant** (`shared/components/chatbot-widget`, customer shell only) is rule-based: no LLM or backend. `core/assistant/assistant-engine.ts` is a pure `answer(text, context)` function (intent regexes over products, services, the customer's bookings, open slots, orders, cart) and `AssistantService` builds that context from the live signals. Topic chips on the welcome screen are `ASSISTANT_TOPICS` in the engine, and every suggested question and follow-up must be something `answer` handles (it never falls through to the "not sure" reply). Replies carry optional product cards, links and follow-up chips; links into the catalog use its `?q=`, `category`, `min`, `max`, `stock=1` and `product=<id>` query params. It deliberately doesn't state returns/warranty policy (unknown).
- IDs: `User.id`, every field that references a user (`customerId`, `senderId`) and `Product`/`Service`/`Booking`/`Conversation`/`Message` ids are **string Firebase ids**; `Order` ids are string Firestore ids too (people read `Order.code`, e.g. `ORD-0007`, from the sequential `number`). Timestamps are ISO strings.
- `core/models/` interfaces are the single source of shapes; import from the `core/models` barrel.
- `CartService` is a mix of signal + plain getters (`count`, `subtotal`, `shippingFee`, `total`); `SHIPPING_FEE` (top of that file, **mirrored in `functions/src/payments.ts`**, which is what actually charges it, so change both) is **0 since 2026-10-23**: checkout charges only the products and the Shipping row is hidden while it is 0 (orders placed before keep and show their ₱250). Making the fee editable by admins is a planned follow-up. Quantities are capped at the product's live stock (`maxQty`); `addItem` returns `false` when the cap is hit.

**Backend direction: Firebase.** The modular `firebase` SDK is used for auth, user profiles, products, favorites, addresses, bookings, chat and orders. `core/firebase/firebase.ts` exposes `FIREBASE_APP`, `FIREBASE_AUTH`, `FIRESTORE` and `FUNCTIONS` injection tokens (`inject(FIRESTORE)` inside a service). `@angular/fire` is deliberately not used: its stable release (20.x) only supports Angular 20 and 21 is still `-rc`. The app is zoneless, so no zone wrapping is needed around SDK calls. Config lives in `src/environments/environment.ts` (`firebase` block + `useEmulators` flag → Auth on `localhost:9099`, Firestore on `localhost:8080`, Functions on `localhost:5001`; the Firestore emulator needs Java, which isn't installed on this machine); the values there are the real web config for Firebase project `iotel-e9a72`. The local-only `.github/copilot-instructions.md` still describes a Laravel/Sanctum REST API with `HttpClient` interceptors; that is stale. Use the `angular-firebase` skill for the migration.

## Conventions worth knowing

(The full Copilot docs live in `.github/`, which is **gitignored** — treat this section as the durable copy.)

- All components standalone + `ChangeDetectionStrategy.OnPush`; `inject()` only (no constructor injection); `@if/@for/@switch` control flow with `track`; signals for component state (no `BehaviorSubject`); reactive forms for anything non-trivial. The codebase follows this almost everywhere (one leftover `*ngIf` in `catalog.component.html`).
- HTTP/data access only in services, never in components.
- Selector prefix `app-`; files `kebab-case.<kind>.ts`; route constants `SCREAMING_SNAKE_CASE` (`CUSTOMER_ROUTES`); interfaces have no `I` prefix; no `any`.
- Styling split: ng-zorro for tables/modals/forms/tabs/badges, Tailwind for layout/spacing, component SCSS for overrides. Colors are **hex codes only, never named colors** — brand palette: black `#1A1A1A`, red `#CC2020`, gold `#C9A84C`, white `#FFFFFF`, surface gray `#F5F5F5`. Layouts must be responsive.
- **ng-zorro icons are tree-shaken and registered by hand** in `provideNzIcons([...])` in [app.config.ts](src/app/app.config.ts). Using a new `<nz-icon nzType="xxx-outline">` renders nothing until its icon is imported there.
- Product images are served from `public/images/` and referenced as `/images/<file>`.
- Local design/plan docs (per-feature UI spec, phased roadmap) are in `.github/+context/` and `.github/instructions/PLAN.md`; the roles' feature lists in `copilot-instructions.md` are accurate for the UI.
